# mini-harness

一个能跑的最小 Harness。教程里所有代码都来自这里。

它是**自己写的**，不是任何真实项目的源码。目的只有一个：把 Harness 的核心思路用尽可能少的代码讲清楚。

```bash
npm run demo
```

## 里面有什么

```
kernel.ts               内核：插件容器。服务、依赖、事件、环绕式事件、作用域回收
loop.ts                 循环：问模型 → 执行工具 → 结果回灌 → 再问
types.ts                几个共用类型
profile.ts              装配单：几层叠出这次装哪些插件、每个插件配什么
main.ts                 照着装配单把零件装起来，跑一遍
plugins/
  session.ts            会话：只能往后加的事件流，模型历史从它派生
  model-fake.ts         假模型，按剧本回答，每次跑结果都一样
  tools.ts              工具登记处
  tool-files.ts         读文件、删文件两个工具
  tool-count.ts         第 5 课要你亲手写的那个插件
  approval.ts           危险动作先问人（环绕式事件的例子）
  subagent.ts           把一件事分给另一个 agent，它有自己的会话
  logger.ts             把发生的每件事打出来
```

## 几个值得注意的地方

**内核很小。** `kernel.ts` 只管四件事：谁提供了什么、谁在等什么、事件怎么传、拆的时候怎么收干净。读文件、跑模型、问权限，一件都不在内核里。

**循环不认识权限。** 打开 `loop.ts` 搜「权限」，一个字都没有。它只在动手前发一个环绕式事件 `tool/decide`。`approval.ts` 排在那个队列里，看到危险工具就不往下传。把 `approval` 从装配单里删掉，demo 照样跑，只是没人拦了。

**循环自己也是一个插件。** 这一条值得停一下。`loop` 就在装配单最后一行，跑起来时你能在日志里看到它和别人排在一起：

```
ok    plugin/start { name=approval }
ok    plugin/start { name=tool-count }
ok    plugin/start { name=loop }
```

它不在内核里，也不是谁 import 进来的函数——`main.ts` 拿它的方式和拿别的能力一样，`ctx.get<Loop>('loop')`，按名字取。想换一套转圈的规则，写一个也提供 `'loop'` 的插件替掉那行就行，其余插件一个都不用动。

**「一切皆插件，循环也不例外」这句话，指的就是这件事。** 很多框架把主循环写死在内核里，你只能在它留好的几个钩子上挂东西；这里没有那种边界。代价也一并说清：**多一层间接**——想知道这次到底跑的是哪个循环，你得先看装配单，不能直接跳到函数定义。

**环绕式事件和普通事件不一样。** 普通事件（`ctx.emit` / `ctx.on`）只是通知一声，听的人改不了什么。环绕式事件（`ctx.waterfall` / `ctx.intercept`）给每个监听器一个 `next`：

- 调 `next(值)` → 交给下一个人
- 不调 `next` → 短路，后面的人和真正干活的那段都不跑
- 先 `next` 拿到下游结果，再包一层返回 → 也行

运行记录里能直接看出短路发生了。`read_file` 三行齐全，`delete_file` 到 `tool/decide` 就断了，后面两行没有——工具的 `run` 一次都没跑：

```
call  tool/decide { name=read_file, args={"path":"notes.txt"} }
call  tool/before { name=read_file, args={"path":"notes.txt"} }
io    tool/after  { name=read_file, output=记得写测试 }

call  tool/decide { name=delete_file, args={"path":"notes.txt"} }
warn  approval/deny { name=delete_file }
warn  tool/blocked { name=delete_file, reason=用户拒绝了这次操作。 }
```

**模型看到的历史，是从日志里现算的。** `session.ts` 存的不是消息数组，是「发生过的事」——包括 `turn/start`、`step/start` 这种模型根本看不到的结构事件。要喂给模型时，`derive()` 从日志里挑出 `user` / `assistant` / `tool` 三种，现拼一份历史出来。这份历史没有单独存过：

```
日志里一共 14 条事件
派生出来给模型看的只有 8 条消息
```

这么麻烦是有回报的：日志里的信息比消息多（谁先谁后、哪一步属于哪一轮、中间被拦下过什么），所以同一份日志既能喂模型，也能拿去回放、存盘、分叉出一个新会话。

**子 Agent 有自己的会话。** `subagent.ts` 注册了一个 `delegate` 工具。它被调用时开一个**新**会话，而不是往当前日志里接着写。跑完之后三个会话各记各的：

```
--- 三个会话，各记各的 ---           ← npm run demo 的原样输出，改了代码记得回来核
s1（顶层，第 0 层）：日志 14 条，派生历史 8 条
s2（顶层，第 0 层）：日志 11 条，派生历史 6 条
s3（派自 s2，第 1 层）：日志 5 条，派生历史 2 条
```

子会话没带上父会话那一大段对话，所以它那份历史短得多。传回父会话的只有一样东西：子 Agent 的那句结论，当成一条工具结果。

**工具出错不会把循环炸掉。** `stat_file` 打不开文件时是直接 `throw`，不是返回一句错误提示——工具是别人写的代码，它想抛就抛。`loop.ts` 把 `tool.run` 包在 `try/catch` 里，抓到之后把错误当成这次工具的结果还给模型，和「被拦下」走的是同一条路：

```
call  tool/decide { name=stat_file, args={"path":"missing.txt"} }
call  tool/before { name=stat_file, args={"path":"missing.txt"} }
warn  tool/failed { name=stat_file, reason=打不开 missing.txt }
```

没有 `tool/after`，但下一行 `step/start` 照常出现——循环活着，模型看到错误后自己改了口。

**循环有两个出口，不是一个。** 一个是模型不再要工具（`loop.ts` 里 `if (!reply.toolCall)`），另一个是步数走到 `MAX_STEPS` 上限。第二个出口是防模型抽风用的：万一它每一步都要工具、永远不给答案，这里得有个头。

**装配单是叠出来的，插件认配置。** 插件有四样东西，不是三样：名字、要用的服务、`setup`，**外加一份配置**。配置从哪来？装配单。而装配单本身是一层层叠出来的——底座给一份，用户那层只盖自己在意的那一项：

```ts
const base     = { name: '底座', use: [...], config: { approval: { deny: ['delete_file'] } } }
const trusting = { name: '信任',              config: { approval: { deny: [] } } }
compose([base, trusting])   // 后面的盖前面的
```

`npm run demo` 用两份装配单各跑了一遍**同一个剧本**，零件一个没换，只有一个配置项不同：

```
state approval/config { deny=["delete_file"] }      ← 第一遍
warn  approval/deny { name=delete_file }
warn  tool/blocked { name=delete_file, reason=用户拒绝了这次操作。 }

state approval/config { deny=[] }                   ← 第二遍
call  tool/before { name=delete_file, args={"path":"notes.txt"} }
io    tool/after { name=delete_file, output=已删除 notes.txt }
```

同一套零件，换一层配置就是另一个产品形态。这就是「组装单」的意思。

**装配单的顺序无所谓。** `main.ts` 里故意把 `tool-files` 写在 `tools` 前面。它依赖的服务还没有，就先排队等着；`tools` 装好之后内核会自动回头把它装上。运行记录第一行就是这个：

```
warn  plugin/wait { name=tool-files, missing=["tools"] }
ok    plugin/start { name=tools }
ok    plugin/start { name=tool-files }
```

## 它没做什么

这是教学用的骨架，不是能用的产品。**每一块都比真货简化了很多**，下面逐条说清差在哪，免得看完 demo 以为就懂了真实的 Harness。

| demo 里的样子 | 真实的 Harness 还要做什么 |
|---|---|
| **内核**：服务、依赖、两种事件、拆插件回收 | 多几种事件分发方式（要不要等、要不要返回值都不一样）；插件树有层级，一棵子树能整体挂载和卸载；配置从文件读，改了能热重载 |
| **环绕式事件**：同步、只有一个 `tool/decide`，监听器要么放行要么短路 | 真实语义还多两样：监听器可以先 `next()` 拿到下游结果、加工之后再往外返（我们这里没人这么用）；分发方式也不止一种，有的要等所有人跑完、有的不等，有没有返回值也不一样。另外一次工具调用要过好几道关，不是一道：先是可以放行/拒绝/问人的那道，再是只能拒绝、拒了就翻不回来的那道，然后才是超时重试这类包在外面的一层；沙箱是另一条线，管的是被启动的进程能碰到什么 |
| **会话日志**：内存里一个数组，六种事件 | 事件种类多得多，插件还能自己加；原始的流式分片也逐条落盘（所以能逐字回放）；写磁盘要分批、要校验、崩溃后能修；上下文太长时会「遮蔽」掉一段而不是删掉，日志始终是完整的 |
| **派生历史**：每次全量重算 | 算过的部分会缓存；被遮蔽的那段不出现在模型历史里，但回放和界面读的是另一份投影，看得到全貌 |
| **子 Agent**：开个新会话，问一次模型 | 委派方式不止一种——可以全新开一个，也可以从当前对话的某个位置分叉出去，还可以交给另一个产品去做；有的子 Agent 跑完就结束，有的能存下来以后接着聊；父子关系、隔了几层这些都要落盘，重启后还在 |
| **循环**：一个 `for`，一句话进来跑到底。「轮」和「步」在我们这儿是一回事 | **层数就不一样**：真实的是「轮次」套「步骤」两层，轮次之上还有第三层（承载一整个轮次的外层策略迭代，比如「为了达成一个目标反复来几轮」）。而且**一个轮次可以一个模型请求都不发就结束**——输入被拦下、被取消、或者根本没有有效输入，轮次照样开了又关。我们这个 `for (let step = 1; ...)` 表达不了「零步骤的轮次」这件事。此外：进来的消息要排队，有的插进去会立刻唤醒它，有的要等下一次才捎带上；模型返回是流式的；失败要能重试，取消要能等它真的停下来 |
| **模型**：按剧本回答 | 真的网络请求、多家提供方、每家的重试策略不一样 |
| **装配单**：`profile.ts` 里两层叠一叠，`main.ts` 里照单装 | 层数更多也更正式：底座一层、界面一层、用户自己一层、命令行再盖一层。配置写在文件里不是代码里，**改了不用重启，热重载**。而且插件是按名字从磁盘装的，不是像我们这样 import 进来 |
| **只有一个入口** | 同一套内核可以配不同的「脸」：网页界面、跑一次就退出的命令行、给别的程序调用的服务 |

一句话：**demo 是骨架，真货是骨架上长满了东西。骨架的形状是对的，但别把骨架当成全部。**
